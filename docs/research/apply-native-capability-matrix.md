# Can native tools replace Apply?

The tables record the pre-removal audit at `c4ccbf9`. LPT-403 then fixed empty-file creation and removed Apply under the approved native contract. Historical differences below are evidence, not current API promises.

## Answer

**Native tools replace the agreed practical workflows, not every historical Apply guarantee.** The user chose to retire grouped undo and aggregate transfers, keep native batching semantics, fix empty creation, and remove the duplicate tool.

The audit found three major differences. The first two were dropped from the required replacement contract; the third was fixed before removal:

1. Native batches do not produce grouped undo receipts. `undo last` cannot restore an Apply checkpoint containing several files, file creation/deletion, moves, or binary files.
2. Native text copy/move pairs ranges. Apply concatenates sources and broadcasts the result. JavaScript can build the same destination text, but that alone does not preserve source guards or a coherent multi-file move.
3. Creating a new empty file with native `write` creates the file but reports a failed batch. A tested temporary-file composition avoids that failure and refuses overwriting an existing destination, but adds intermediate effects and is not a transaction.

Other differences are intentional or can be handled by composition. In particular, committing accepted edits after an ordinary script error is already the approved [native batching policy](native-codemode-batch-decision.md). It should not be changed silently to imitate Apply.

This audit does **not** require preserving every historical Apply behavior. The user chose the native contract and important practical scenarios, not full historical compatibility. The tables below keep the observed differences visible; the approved removal contract at the end says which ones still matter.

## How to read the historical matrix

- **Covered**: an existing native mechanism covers the operation. This is not a claim of identical execution guarantees.
- **Compose**: ordinary tools plus JavaScript can express the operation; the stated caveats still apply.
- **Different**: both routes exist, but their observable behavior differs.
- **Gap**: there is no replacement for the stated guarantee in the current native API.
- **Unproven**: a proposed replacement has not been checked end to end.

The public inventory comes from [Apply's runtime bindings][apply-runtime], not just its prompt. `editorOpen`, `editorResolve`, and `editorApply` are private bridges. `__finishApplyScript` is an internal completion hook. There is no public `result()` helper bound by this runtime; Read/Search/Diff results are recorded automatically.

### Snapshot-safe composition rules

A matching final string is not enough to establish parity:

- Check `status`, `effect`, completeness and the parent final batch outcome. Native domain errors can resolve instead of rejecting the JavaScript promise.
- Use a returned stored target or a filtered array of complete returned items. Read context and preview text do not create new editing authority.
- Retain original source/snapshot guards when reconstructing text. Replacing only the destination does not check that the source still matches the text you copied.
- Read's default target is its returned window. A whole-file target can be obtained through Select on the file, but any paged reconstruction must stay tied to that target and preserve line endings. This bulk composition was not executed here.
- For exact `find`, escape quotes/backslashes inside a quoted Search term rather than relying on JSON's `\n` escape decoding. Check arbitrary multiline cases before replacing Apply's literal scanning.
- A sequence of successful calls is not an atomic transaction. Compensation code can itself fail and does not replace a preflight-guarded grouped undo receipt.

**All eight checks passed across focused runs, not in one uninterrupted eight-test run.** Passing P3 means the audit reproduced the bug; it does not mean empty native creation works correctly.

The run history is intentionally kept honest:

- First six-check run: no scenario could start because `node-pty` had not been built after the local install with scripts disabled. Building that dependency fixed the environment, without repository source changes.
- Retry: five passed; one assertion used the wrong Apply result envelope. Correcting it proved P6 in isolation.
- New creation workaround exposed P3. The first workaround used a literal selector before a pending file creation had committed; the replacement failed and the file contained `seed`. The final version checks child statuses and replaces through the returned pending write target; P5 then passed.
- Only targeted serial runs were used: `env -u PI_INTEGRATION_TEST_RUNNER pnpm exec vitest run --config vitest.integration.config.mjs --maxWorkers=1 --no-file-parallelism`. No shared runner pool, shards, or full-suite rerun.

## Approved removal contract

The user reviewed the matrix and chose:

1. **Drop grouped checkpoint undo.** Do not add a native grouped receipt producer just to preserve Apply. Existing per-file text undo is a separate capability.
2. **Keep equal-pair copy/move.** Concatenating sources and broadcasting to all destinations is not a required native operation.
3. **Fix empty-file creation separately before removing Apply.** The temporary-file composition is evidence of a workaround, not the chosen permanent API.
4. **Keep the native error/checkpoint/target model.** Ordinary errors keep accepted surviving edits; checkpoints are global/automatic; targets never silently refresh. Remove old Apply promises from removal-facing docs and examples.
5. **Check the native contract and important practical scenarios.** Do not chase full compatibility with every historical helper or convenience rule. The unproven areas above remain honest limitations, not automatically mandatory new features.

### Removal implementation

- Fixed empty native creation. The standalone and Codemode regressions check actual zero-byte content, truthful applied effects and a usable point target. See [empty creation tests](../../tests/integration/native-empty-write.integration.test.ts).
- Removed Apply registration, runtime, grouped undo receipts, private plugin APIs, preview settings and dependencies. Ordinary editing, Diff, Git change undo and per-file last undo remain.
- Migrated practical shared integration scenarios to native tools. The removal checks cover post-edit processing, scoped semantic/AST operations, module settings, user hooks, CRLF insertion, native result schemas, discovery and hidden-tool boundaries, resource scheduling and progressive guides.
- Kept the native contract: strict snapshots, equal-pair transfers, global checkpoints and final processing once per surviving resource. Ordinary errors keep accepted edits; cancellation discards only pending work. There is no grouped rollback or silent syntax repair.

Historical audit checks below were not rerun after removal: they deliberately depend on the old Apply runtime, and P3 reproduces the old empty-write defect. Their source stays in Git history. The original serial removal check passed 58 contracts and failed one outdated hook expectation; targeted retries verify the corrected native Read/error and blocked-commit behavior. Final live and check evidence is recorded in the task Workpad. No full suite was run for this removal.

Full historical equivalence remains false by design. That is not the accepted product requirement.
