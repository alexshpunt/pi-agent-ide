# SSH backend work in progress

This directory is the transport foundation for LPT-149. Its explicit registration bridge connects configured SSH targets to the existing read and text mutation tools. The built-in read.ssh module loads a separate ssh.json beside each global/project extensions.json. Other IDE capabilities are still unfinished; this does not satisfy the full task matrix.

`identity.ts` keeps target IDs separate from remote paths and escapes filename characters in `ssh://` references. Paths resolve against a remote workspace without using the local platform's path rules. Remote paths are POSIX-shaped on every target: a Windows path keeps its drive as the first segment (`/C:/Users/name`, shown as `ssh://win/C:/Users/name`), so path joins and relative paths stay valid, and resolution never leaves the drive. Only configured target aliases will be allowed by the provider registry.

Each target declares `os` (`linux` by default, or `windows`). The OS selects path rules, the interpreter command and the platform modules sent to the target.

`ssh.ts` runs short framed operations with system OpenSSH and transient Python code. Authentication stays in SSH config, known_hosts and the user's agent. Requests travel on stdin, not inside interpolated shell commands. Raw SSH diagnostics never become public errors. A nonzero application exit remains an application result.

## Connection reuse

On Linux and macOS controllers, every SSH process goes through an OpenSSH master that Pi starts for the target (`ssh-master.ts`), so a request costs no handshake. A master carries up to 8 sessions (OpenSSH servers refuse the 11th by default); when all are busy, Pi starts another, up to 4 per target, or a process waits up to 2 s for a free session and then connects directly. The first process to a target waits for its master within its own startup deadline.

A master runs in the background (`ssh -f -N` with `ControlPersist`) behind a socket in `/tmp/pi-ssh-<uid>`, a directory only this user may own and use; a socket path must stay under about 104 bytes. Pi stops its masters with `ssh -O exit` when its process exits. After an extension reload, Pi starts new masters with new socket names, while the earlier masters keep serving the channels opened before the reload and stop at exit with the rest. A master left by a crashed Pi exits 60 s after its last session, and the next Pi removes sockets nobody listens on. A master whose socket stops answering is replaced; a dead network ends a master after the user's `ServerAliveInterval` × `ServerAliveCountMax` for the target, or after 45 s (15 s × 3) when the user's configuration sets no keepalive. A master carries every process to the target, so a shorter window would end them all on a brief network gap that a direct connection survives. OpenSSH connects directly when a socket refuses a session, and a process that loses its master before the worker handshake is retried once directly, because nothing ran on the target yet.

A user whose SSH configuration sets `ControlMaster` or `ControlPath` keeps that setup; Pi starts no master then. A master that fails to start, for example on an authentication error, makes processes connect directly for 30 s, so they report the same classified error as before. Windows OpenSSH cannot multiplex, so a Windows controller opens a new connection for each process.

## Lost connections

OpenSSH runs at `LogLevel=VERBOSE`, so its stderr shows when it authenticated and how a connection ended. A lost connection reports `TRANSPORT_FAILED` with a classified reason (keepalive timeout, reset, closed by the target, broken pipe, TCP timeout, refused, unreachable, unresolved), the phase it reached (connecting, starting or running), the time since the attempt began and the time since the target last sent anything (`ssh-connection-loss.ts`); OpenSSH's own text stays inside the backend. A process that goes through a master sees only the master's socket close, so it reads the end of the master's log instead: each master writes it at `LogLevel=VERBOSE` beside its socket (`-E <socket>.log`), and Pi removes it with the socket. A master runs without stderr, where OpenSSH reports a connection the target closed, so a log that shows the end of the connection and no other reason counts as closed by the target. When the network breaks a connection while it is being set up, before OpenSSH authenticated and before the target sent anything, nothing ran there: the worker sends its handshake before it reads the request. Such a connection is retried twice, after 1 s and 2 s, within the same startup deadline. A refused port, an unknown host or an unexplained failure gives the same answer on another attempt and is not retried.

## Remote bootstrap

Every operation starts with one fixed remote command, `<interpreter> -c "import sys;exec(sys.stdin.buffer.raw.readline())"`. It contains no characters that bash, fish, sh, cmd.exe, Windows PowerShell or pwsh would expand, so the target's login shell does not matter. The interpreter is `python3` on Linux; on Windows it is `py -3`, then `python`, because `python3` there is often the Microsoft Store alias. The interpreter that reaches the handshake is remembered per destination.

The first stdin line is a small loader. It prints a `pi-agent-ide-worker:` handshake with the target platform, refuses a platform that does not match the declared OS (`TARGET_OS_MISMATCH`), then reads a length-prefixed program. Output before the handshake, such as shell profile messages, is discarded. Before the handshake nothing has run on the target, so a missing interpreter (`DEPENDENCY_UNAVAILABLE`) is `not-applied` and the next candidate can be tried. Only OpenSSH's own exit status 255 is a transport failure.

Programs are bundles: `ssh-transport.ts` combines an entry with named modules, served to `import` from memory. The channel worker is `ssh-channel-worker.py` with `ssh_channel_common.py` and `ssh_channel_posix.py` or `ssh_channel_windows.py` as `ssh_channel_platform`; the file worker is `ssh-worker.py` with `ssh_worker_common.py` and `ssh_worker_posix.py` or `ssh_worker_windows.py` as `ssh_worker_platform`. `ssh_paths.py` converts `/C:/...` paths at the Windows boundary.

Worker sources are read when their module loads (`packaged-source.ts`), and the SSH modules import each other statically. A running Pi therefore keeps using the code it loaded after its checkout or package changes on disk. A worker or module read on first use could come from the newer version and disagree with the loaded code about its protocol.

Other IDE Python programs run as `remotePython(source)` commands. The channel worker starts them with `-u -c` and a short loader, then writes the length-prefixed source to their stdin before caller input, so program size never meets the Windows command-line limit. On Linux the channel resolves `python3` from PATH as before; on Windows it reuses its own interpreter.

The Windows channel supports pipe services and PTY sessions. A PTY session runs behind a ConPTY pseudoconsole with resize, and Ctrl+C written to its input reaches the shell; the child gets null standard handles and Ctrl+C handling restored, because the worker's own stdio is redirected and may have Ctrl+C ignored. Every process is created inside a Job Object: PTY children through the job-list attribute, pipe children suspended until assigned. So descendants are owned from their first instruction and end with the leader, a stop request or the channel. Pipe commands are resolved through PATH and PATHEXT without the current directory, so `.cmd` shims such as `npm` start by bare name; an npm-style shim runs as its Node script, and any other batch file runs through cmd.exe and refuses arguments with batch metacharacters. The terminal provider runs Windows PowerShell (`powershell.exe -NoLogo -NoProfile -Command`) on Windows targets.

The Windows file worker supports every operation the POSIX worker does, including `git-query` and the guarded `gitIndex` write (Git's `index.lock`, then `os.replace`). It takes `ssh_windows_files.py` as an extra module. A Windows target receives `ssh-transfer-worker-windows.py` for streamed transfers, bundled with the same module.

Windows file semantics:

- Identity is the volume serial and NTFS file index. A revision covers the resolved path, identity, mode, size, modification time and attributes. Modes are reported as POSIX modes without group and other write bits (`0644`, `0444`, `0755`); a source without owner write access becomes a read-only file.
- Writers are serialized with named mutexes (`Global\pi-agent-ide-<hash>`), one per directory and one per file identity, acquired in sorted order with a 20 s wait. A mutex whose owner died is taken over by the next waiter.
- A file is replaced with `ReplaceFileW`, which keeps the replaced file's attributes, ACL, alternate data streams and creation time; a missing destination is created by rename. A destination with other hard links is rewritten in place, as on Linux. A read-only destination is refused before any change (`FILE_READ_ONLY`); a sharing violation reports `FILE_IN_USE` with effect `not-applied`. Only `ReplaceFileW` failures that leave the replacement half done are `unknown`.
- Symbolic links and junctions are `symlink` entries. Recursive removal never follows them and checks each directory's type and identity immediately before and after listing it, but a swap between those checks is not impossible. Read-only files inside a removed tree are cleared first. A link from a POSIX source is created with `\` separators; creating one needs the symbolic-link privilege (`SYMLINK_NOT_PERMITTED`).
- Names that differ only in case are one name. A same-directory rename that only changes case is allowed for `move` and `move-object`; the controller marks such targets with `caseInsensitive`. Paths of 240 characters or more get the `\\?\` prefix.
- A CRT read refused on an open file means a locked byte range and reports `FILE_IN_USE`.

File snapshots include bytes, resolved path, inode and metadata. Writes check the snapshot immediately before replacement. Directory locks serialize these backend writes. This does not eliminate an external writer racing after the check. Reads reject non-regular files; range reads and directory listing are separate operations. Text replacement follows a symlink's target, while whole-file removal rejects symlinks.

Text snapshots and short-command capture have a 32 MiB bound; chunked file transfers remain unfinished. Original-byte reads use bounded 4 MiB ranges and can cross the snapshot bound without content conversion. Byte ranges do not promise one immutable snapshot across calls; inode or metadata changes within a range or between chunks fail rather than returning a mixture of observed revisions. Atomic replacement preserves extended attributes. Hard-linked files are updated in place under an inode lock so all linked names keep their identity; these writes are not atomic, and interruption may leave a partial unknown effect. ACL-specific and interruption checks still need broader coverage.

`ssh-channel.ts` provides transient framed service stdio with ordered remote-acknowledged input, output backpressure, separate binary streams and owned-process cleanup. Its stream size is not the snapshot bound. Startup has a deadline; service lifetime lasts until exit, stop or cancellation. Queued input is bounded to 1 MiB, so callers must await writes and split larger payloads. Remote program exit 255 is distinct from SSH transport failure. PTY channels support controlling-terminal setup, dimensions, resize and foreground control keys. A PTY cannot half-close stdin independently of its shared terminal master; end() rejects without changing the process. The terminal provider uses these PTY channels when `bash` receives a remote `cwd`. Sessions share the existing output logs, screens, input and cleanup paths. Remote PID metadata stays separate from local process ownership. A foreground wait cancellation leaves the session running in the background. LSP and DAP integration, transport-loss recovery and live terminal UI verification remain unfinished.

## Checks

```sh
pnpm exec vitest run src/backend/identity.test.ts
pnpm exec vitest run --config vitest.integration.config.mjs tests/integration/ssh-backend.integration.test.ts
```

The integration fixture starts an isolated loopback sshd with disposable keys and host configuration. It does not edit user SSH files or connect a user's server. On a root Linux runner it uses the existing `agent` account; otherwise it uses the current unprivileged account. It needs system sshd, ssh-keygen, Python 3 and a usable PAM account. Missing fixture dependencies fail setup rather than silently skip SSH verification. Fixture files live in a disposable `.tmp` directory under the system temporary directory so the unprivileged account can reach them.

### Linux and Windows directions

Two tests run in each direction, written `source>target`: `linux>linux`, `linux>windows`, `windows>linux` and `windows>windows`. `tests/integration/ssh-platform-matrix.integration.test.ts` checks the backend contract: byte reads, listings, program runs, the service channel and, on Windows, a file held open by another process. `tests/integration/ssh-platform-tools.integration.test.ts` uses the IDE tools through real Pi: edits with stale-revision refusal, copy, move and delete, file and directory transfers in both directions, a terminal session with input, line-by-line terminal text, a save without a configured formatter, and Git staging and undo. The source is the machine running Pi; the target is the SSH server. `tests/integration/support/ssh-target-fixture.ts` starts a disposable server for each direction with its own keys, configuration, known hosts and workspace; it does not touch user SSH files, the Windows sshd service or `ProgramData\ssh`.

| Direction         | Server                                                                             | Needs                                                                                                                        |
| ----------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `linux>linux`     | the loopback sshd above                                                            | system sshd, the `agent` account                                                                                             |
| `windows>windows` | `sshd.exe -D -f <private config>` on localhost                                     | Windows OpenSSH Server and `py -3`                                                                                           |
| `windows>linux`   | sshd inside WSL 2, started through `wsl.exe` and reached on localhost              | a default WSL distribution with sshd, Python 3 and an `agent` account (`PI_SSH_WSL_DISTRO` selects another)                  |
| `linux>windows`   | `sshd.exe` started from WSL through interop and reached at the WSL gateway address | Pi inside WSL on a Windows host; an administrator account, because the fixture adds and removes a firewall rule for its port |

`PI_SSH_COVERAGE_DIRECTIONS` lists the directions to run. A listed direction that cannot start, or one this machine cannot be the source of, fails the run; nothing is skipped. Without the variable the test runs the directions this machine can serve: `linux>linux` on Linux, plus `linux>windows` inside WSL, and both Windows-source directions on Windows. `PI_SSH_COVERAGE_WINDOWS_HOST` names a trusted OpenSSH alias of a Windows host to use as the Windows target instead of a disposable server, for example from a Linux machine without WSL interop; the tests work in a new temporary directory there and remove it.

The `SSH platforms` workflow (`.github/workflows/ssh-platforms.yml`) runs all four on a `windows-latest` runner in two parallel jobs: a Windows source and a Linux source inside WSL 2. It runs for changes to this directory, the terminal plugin and the fixtures, takes about eleven minutes, and is separate from the main CI workflow.
